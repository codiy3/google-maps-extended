# 複数路線・接続先・データ保存

更新日: 2026-09-13。開発版の実装範囲と制約を記録する。

## 確定した方針

- Googleマップは利用者が保存したDemo Keyで検証する。通常キーへの変更は全実装後に利用者が行う。
- ODPTの登録・APIキー・通信を起動条件にしない。将来の接続用に `RailwayProvider` の境界を残す。現時点の `OdptProvider` は無効であり、キーを設定しただけでは動作しない。
- AIやLLMによる駅順・直通・所要時間の推測は採用しない。
- 保存できる基礎データをSQLiteへ格納する。Googleの駅・経路データを恒久保存する実装にはしない。

## 駅順と路線名

N02の路線区分は、利用者が乗車する運行系統と一致するとは限らない。東京メトロの表示名から「8号線」などの接頭辞を除き、原典名は検索別名として保持する。

| 有楽町線 | 和光市〜新木場 | 24 | [公式駅一覧](https://www.tokyometro.jp/station/line_yurakucho/index.html) |
| 副都心線 | 和光市〜渋谷 | 16 | [公式駅一覧](https://www.tokyometro.jp/station/line_fukutoshin/index.html) |
| 千代田線 | 代々木上原〜北綾瀬 | 20 | [公式駅一覧](https://www.tokyometro.jp/station/line_chiyoda/index.html) |

副都心線の和光市〜小竹向原はN02の有楽町線の形状から構成する。各隣接駅を実際の原典線形のグラフ上で接続し、欠けた線形を直線で補わない。千代田線の綾瀬では常磐線方面と北綾瀬方面を区別する。全列車が一覧の両端を走る意味ではない。

照合が済んでいない路線は引き続き「駅名順・停車順未確認」と表示し、始終点に見える連番を付けない。全国の運行系統の完全性を保証する段階ではない。

## 路線選択と駅の接続

1. 検索候補を選ぶと表示中の路線へ追加し、左の詳細をその路線へ切り替える。
2. 選択済みの路線を選んでも重複追加しない。各路線の「×」で、その路線だけ地図から外す。
3. 地図には選択済み路線を色分けして重ね、赤ピンの横に駅名を常時表示する。最初の色は緑で、追加した路線に別の表示色を割り当てる。原典の同一駅グループはピンを共有し、同名というだけで他地域の駅を統合しない。
4. 駅を選ぶと、接続する路線と鉄道会社を表示する。リンク先を選ぶとその路線を追加・選択して同じ接続駅へ移動する。
5. 駅名検索でも所属する複数路線を候補表示する。代々木上原では小田原線・千代田線、和光市では東上本線・有楽町線・副都心線を選べる。
6. 種別のフィルターは詳細を開いている路線に適用する。他の選択路線は全駅を表示する。

表示色は鉄道会社の公式色を意味しない。左側の路線名の凡例・線路・駅名ラベルに同じ色を使い、他路線の追加・解除で選択済み路線の色を変更しない。同じ座標の線形は、太い下地から重ねて各路線の色を残す。共用駅のラベルには所属する表示路線の色だけを添える。駅名が重なる縮尺では地図を拡大して確認する。

駅の吹き出しは上部に「和光市駅」のような見出しを表示する。吹き出しの閉じる操作とEscapeは起点の選択も解除する。

乗り換えはN02の同一駅グループを根拠とする。改札内外や移動経路を個別には検証していないため、所要時間やバリアフリー経路を保証しない。

直通は同一駅や線路の近さから推測せず、別の台帳に記録する。現状はメトロ3路線と小田急・JR常磐線・東武東上線・西武有楽町線・東急東横線の接続地点を対象とする。例として[小田急の公式説明](https://www.odakyu.jp/town-life/feature/)で代々木上原経由の千代田線・常磐線との直通を確認した。常磐線で直通対象となるのは各駅停車系統であり、リンク先のN02原典路線の全区間へ直通する意味ではない。

路線の端に接続があれば駅一覧の前後に、途中の接続は「途中駅での直通」と駅詳細に表示する。「直通する列車・行先に限る」を常に併記する。全国の直通台帳は未完成であり、記録がないことを直通なしとは判断しない。

## SQLiteと再試行

保存先はアプリ内の `data/local/railway.sqlite3`。Gitには追加しない。

- 初回起動で生成済みの `public/data/` を検証してDBへ取り込む。
- 通常の検索・路線表示はDBを読む。ブラウザ内でも取得した路線を再利用する。
- 基礎データが更新された場合は `dataRevision` を含む索引のハッシュを比較し、トランザクション内で更新する。破損・不完全な更新では旧DBを残す。
- 読込エラーの再試行は、取得済み原典から生成したローカルJSONを検証してDBへ復元する。成功後に再試行ボタンを消す。
- 現在の再試行はGoogle APIからの補完ではない。公開データの外部API取得も自動では実行しない。
- 取得済みZIP自体が未取得・破損の場合は `setup.command` またはデータ再生成手順を案内する。

`npm run dev` はuvで作成した `.venv/bin/python` のローカルAPIとViteをまとめて起動する。Python APIは127.0.0.1の空きポートで待ち受け、起動ごとのトークンを付けたViteプロキシ経由で利用する。Ctrl+Cで両方停止する。SQLiteはPython標準ライブラリを使用し、追加サービスへの登録は不要。

GoogleのPlaces・Routesは、応答の保存に制限があり、Place ID等が例外となる。本アプリはGoogle応答をSQLiteへコピーしない。[Placesの条件](https://developers.google.com/maps/documentation/places/web-service/policies)、[Routesの条件](https://developers.google.com/maps/documentation/routes/policies)

## 所要時間の現在地

駅詳細に同一路線の全駅への所要時間欄を実装する。日本時間の出発日時から2時間に出る同じ便で、乗降可否・停車順・運転日を確認し、比較可能な正確な予定時刻の最短乗車時間を求める。待ち時間・乗換時間を含めず、途中停車時間を含める。異なる便の駅間最短値は足し合わせない。

駅を選択している間は、選択路線に属する地図上の駅名ラベルにも予定到着日時と乗車時間を表示する。各到着駅に対して選んだ最短乗車時間の便の予定到着であり、全駅を同じ便で回る案内や最も早い到着時刻ではない。左側の一覧と地図は同じ検索条件・応答を共有し、日付をまたぐ発着を日本時間の日付付きで表示する。時刻表がない場合は「到着時刻未取得」、確認中・取得失敗はそれぞれ区別し、他路線に結果を流用しない。起点・日時・種別が変わったら以前の結果は表示しない。

ただし実在路線の時刻表はまだ収録していない。現状は「時刻表未取得」を表示する。推定・欠落・未確認の便を0分や便なしとして扱わない。Demo KeyでGoogle地図表示は成功したが、Compute Routesの1回の検証は `403 PERMISSION_DENIED` であった。Googleの設定・課金・制限は変更していない。この応答だけで日本全域のAPI非対応とは断定しない。

将来、保存可能な時刻表を `railway_data/timetable.py` の共通形式へ変換してSQLiteに取り込む。ODPT、GTFSなどの変換器は別途の実装・実データ検証が必要。API境界は残すが、ODPT接続が完成しているとは扱わない。

共通形式は `schemaVersion: 1`、`routeId`、`provider`（保存権限を確認した `licensed-open-data` または `user-owned`）、`sourceUrl`、`license`、`retrievedAt`、`validFrom`、`validUntil` と `trips` を持つ。便は `id`、`serviceId`、明示的な `serviceDates`、順序を保持する `stops` を持つ。停車には `stationId`、到着・発車の `HH:MM:SS`（24時以降可）、`precision`（exact/estimated/unknown）、`pickup`、`dropoff` が必要。運転日の祝日を曜日だけから推測しない。

取り込み例（データの保存権限・有効期間を確認した開発者向け）:

```sh
source scripts/env.sh
uv run --locked python -m railway_data.timetable /path/to/normalized-timetable.json
```

テスト用の架空の分数は実アプリのDBへ入れない。全国の所要時間・種別の実データ対応は、今後のデータ整備として残る。
