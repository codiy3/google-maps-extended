# 開発・コミット運用

## ブランチ

- 基本ブランチは`main`。
- 設計資料の修正を含め、変更は`codex/<作業内容>`のブランチで行い、PRでレビューしてから`main`へマージする。
- ユーザーの既存変更を破棄しない。
- 履歴を残すため、理由なくコミットをまとめたり履歴を書き換えたりしない。

## コミットの粒度

1つの変更目的に対して1つのコミットを基本とする。ファイルごとに機械的に分割せず、説明・検証・取り消しが可能な単位を選ぶ。

例:

1. `chore: リポジトリの基本設定を追加`
2. `docs: 要件と開発手順を記録`
3. `chore: uvのPython環境を固定`
4. `docs: 起動方法と画面構成の案を記録`
5. `chore: ReactとTypeScriptの開発環境を追加`
6. `feat: 全国路線データの変換処理を追加`
7. `feat: 路線候補の検索を追加`
8. `feat: 全駅の赤ピン表示を追加`
9. `feat: 線路の緑色ハイライトを追加`
10. `test: 環状線と支線の整合性を検証`
11. `feat: 路線ごとの種別と停車パターンを取り込む`
12. `feat: 種別フィルターと一部停車の表示を追加`
13. `feat: 日時指定の列車比較を追加`
14. `test: 運転日と停車判定の例外を検証`

コミット件名は日本語で簡潔にする。必要なコミット本文には変更理由と実施した検証を残す。作業の区切りごとにGitHubへpushする。

## コミット前

1. `git status --short`と`git diff`で変更範囲を確認する。
2. 変更に適したformatter、lint、型チェック、テストを実施する。
3. 設定・ドキュメントのみの場合は構文、相互整合性、`git diff --check`を確認する。
4. 設定例に実際のAPIキーやトークンが含まれていないことを確認する。
5. 対象ファイルを明示してステージする。
6. `git diff --cached`と`git diff --cached --check`を確認する。
7. コミット後の`git status -sb`と`git log`を確認する。

## 検証の導入

Python処理を追加する際にデータ変換・路線接続・重複の検証を導入する。フロントエンド実装時に型チェック、lint、ビルド、必要な操作テストを導入する。全国データの検証結果は、入力版・出典・対象数・不足内容とともに記録する。

起動や実装が未完成の段階では、その状態をREADMEに明示する。

## 自己レビューとマージ

ユーザー指定により、担当者自身がレビュー、GitHubへの指摘コメント、修正、再レビューを行ってからマージする。

1. 変更対象と基準コミットを確認し、専用ブランチでPRを作る。
2. 指摘には対象ファイル・根拠・具体的な発生条件・影響・修正方針を記載する。自己レビューであることを明記する。
3. PRに指摘を投稿した後、修正を意味のある単位でコミットする。指摘と対応コミットを関連付けて返信する。
4. 変更に応じた検証を行い、最新コミットを再レビューする。追加指摘があれば同じ手順を繰り返す。
5. PRの最終説明と検証結果を更新する。設計の確認と実装の動作確認を区別する。
6. 未対応の指摘がなく、差分・利用可能なチェック・競合状態を確認できたらマージする。必須チェックや他者レビューが設定されている場合は、その条件を満たす。
7. 小さいコミットの履歴を保つため、原則としてマージコミットを使う。レビュー済みの先頭コミットが変わった場合は差分を再確認する。
8. GitHubのマージ状態を確認し、ローカルの`main`をfast-forwardで同期する。

GitHub上の自己コメントを、第三者による承認レビューとは扱わない。未設定のCIや未実装機能について、チェック成功・動作確認済みと報告しない。
